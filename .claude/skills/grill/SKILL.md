# Grill

「何かおかしい気がするが、何がどうおかしいのかはまだ言語化できていない」という状態の著者と一緒に文章を直していくための、汎用的な進め方。論文に限らず、ドキュメント、メール、READMEなど、どんな文章にも使える。

対象はあくまで書かれた文章(prose)そのもの。設計方針やアーキテクチャの選択、実装方法についての壁打ちにはこの進め方をそのまま適用しない — それらは前提の性質が違う(トレードオフの比較や技術的制約の検討が中心になる)ため、別の進め方が必要になる。

## 基本の流れ

1. **違和感 → まず質問、勝手に推測しない。** ユーザーが「違和感がある」「しっくりこない」「grill me」のように指摘したら、いきなり書き直しを提案しない。的を絞った質問(`AskUserQuestion`で2〜4個の具体的な選択肢を出すのが基本。自分に見立てがあるなら「推奨」を明示する)をして、何が具体的に引っかかっているのか、直す方向性はどちらなのかを詰める。

2. **しっくりくる解決策が決まるまで絞り込みを続ける。** 「なんとなく良くなった」ではなく、具体的な方向性が合意できるまで質問を重ねる。

3. **方向性を決めることと、実際に書くことは別のリクエストとして扱う。** 「直して」ではなく「方向性を決めて」と言われたら、その場で編集しない。過去に「今すぐに修正して欲しいわけじゃなくて、修正の方向性を決めて欲しいだけ」と明確に線引きされたことがある。ユーザーが「進めて」と言うまで、決定内容を編集には反映しない。

4. **調べる必要があるかどうかで分岐する。**
   - **調べなくていい**(文章内の情報や一般常識だけで筋が通るかどうかの話) → 自分でその場で直す。
   - **調べる必要がある**(事実確認、引用、外部の情報が絡む話) → 自分で検索したり記憶で埋めたりしない。Perplexity(またはユーザーが実際に使っている検索手段)向けの、的を絞ったプロンプトを書いて渡す。すでにURLが分かっている場合でも、勝手にWebFetch/Readで取得して読みにいかない。URLをそのまま渡すか、取得していいか先に確認する。自分の判断で先に調べに行くのは、ここで避けたい「勝手に進めすぎ」の典型なので厳禁。

5. **スコープを勝手に広げない。** 聞かれたことにだけ答える。たとえば「これまで懸念されていた点について問題ないか」という狭い質問には、その範囲だけで答える。作業中に関係ない別の問題に気づいても、その場で修正に混ぜ込まず、「これは別件ですが」と一言添えて、今扱うか後回しにするか確認する。ユーザーに「話を広げすぎ」と指摘されたら、即座に狭い質問への回答だけに絞り直す。

6. **方向性が決まったら、最小の編集で済ませる。** 新しい説明文を書き足すより、削除や置き換えを優先する。追記は最小限に。すでに引用や前の文で裏付けられている内容を、重ねて説明・定義し直す必要は基本的にない。

7. **編集後は周辺への波及を必ず確認する。** 1箇所直すと近くで綻びが出ることが多い。
   - 引用を減らしたのに「これらの先行研究の多くは」のような複数形の表現が残っていないか
   - 「国内でも」のような、特定の順序や件数を前提にした接続詞が浮いていないか
   - 同じ文の中で著者名を出しつつ、文末でも同じ出典を重複して引用していないか
   - 「示唆している／示している／裏づける／意味する」など、動詞の強さが実際の根拠の強さと釣り合っているか
   気づいたら聞かれる前にこちらから指摘する。
